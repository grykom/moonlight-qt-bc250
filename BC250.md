# Moonlight for BC-250 (experimental)

This unofficial fork starts from Moonlight Qt 6.1.0 with the two upstream
FFmpeg compatibility patches used by the Arch Linux 6.1.0-7 package.
It retains upstream licensing and hardware decoder detection.

## CPU decoding threads

Under Advanced Settings, **CPU decoder threads (BC-250)** offers Auto, 4, 8,
12, and 16. Auto uses up to 8 logical CPU threads. Explicit choices are capped
at the logical CPU count reported by SDL. Selecting 16 on a system exposing
12 CPUs uses 12; using all 16 requires the CPU unlock. The setting does not
unlock the CPU. More threads are not guaranteed to be faster.

The preference is stored as `bc250softwaredecoderthreads` in Moonlight's
existing settings (0 means Auto). Unsupported stored values fall back to Auto.
The effective count is captured for each session and reused for the slice
request, software decoder initialization, and decoder recreation. Reconnect
the stream to apply changes. Hardware decoding keeps its existing behavior.

The slice request log reports what the client requests, not proof that the
host encoder produced that number of slices. Host encoder limits still apply.
An explicit `DECODER_CAPS` environment override retains upstream precedence
and can override the slice request; leave it unset when testing this setting.

The startup dialog about missing hardware decoding is suppressed. Decoder
detection, fallback, and diagnostic information remain available.

## Validation and observations

The settings UI and streaming behavior were tested by grykom on BC-250 with
CachyOS. The startup popup was absent. Session logs showed the selected 4, 8,
12 and 16 thread counts reaching both the slice request and the H.264 CPU
decoder configuration.

An earlier fixed-8-slice trial reported about 11 ms decoding at a 4K120 stream
setting and no more than 5.2 ms at 1440p120, with rendering roughly unchanged.
These are informal observations from that setup, not controlled benchmarks
or a guarantee of sustained 120 FPS. Later testing of the selector showed
substantial variation between games, bitrates and other settings. No single
thread count or percentage improvement is claimed to be best for everyone.

Selected actual log pairs supplied by the tester (timestamps omitted):

```text
Requesting 4 slices per frame for software decoding
BC-250: configuring 4 CPU decoder threads for h264
Requesting 8 slices per frame for software decoding
BC-250: configuring 8 CPU decoder threads for h264
Requesting 12 slices per frame for software decoding
BC-250: configuring 12 CPU decoder threads for h264
Requesting 16 slices per frame for software decoding
BC-250: configuring 16 CPU decoder threads for h264
```

These messages confirm client configuration. They do not measure performance
or prove the number of slices actually emitted by the host encoder.

The thread policy can be checked without Qt or a streaming host:

```sh
g++ -std=c++11 -Wall -Wextra -Werror -Iapp tests/bc250_decoder_threads.cpp -o /tmp/bc250-decoder-threads-test
/tmp/bc250-decoder-threads-test
```

For a streaming test, keep H.264, bitrate, scene, and host settings fixed.
Compare 8, 12, and 16 at 1440p120 and 4K120. Check decoding time, actual FPS,
and dropped frames. Confirm the preference survives an application restart
and the effective count appears in the next session's decoder logs.

Polish strings are maintained in `app/languages/qml_pl.ts`; regenerate the
tracked `app/languages/qml_pl.qm` using Qt's `lrelease` when editing them.

## Arch Linux / CachyOS package

The first package, `moonlight-qt-bc250` version `6.1.0.bc250.1-1`, builds the
tested application commit `f128a1136d4cbad6bc6b47366b5ca9acf77d9de2` and pinned
Linux submodules. Packaging and documentation changes are separate from that
application commit. Existing upstream FFmpeg fixes are already included;
do not apply them again.

For a first build on an up-to-date Arch/CachyOS installation:

```sh
sudo pacman -S --needed base-devel git
git clone --branch bc250 https://github.com/grykom/moonlight-qt-bc250.git
cd moonlight-qt-bc250
```

If you already have the fork checked out, use that checkout instead. From its
root directory, run (works in Bash and Fish):

```sh
mkdir -p "$HOME/moonlight-bc250-package"
cp packaging/arch/PKGBUILD BC250.md "$HOME/moonlight-bc250-package/"
cd "$HOME/moonlight-bc250-package"
env MAKEFLAGS=-j8 makepkg -si
```

`makepkg` must run as your normal user. It downloads the pinned sources,
installs missing dependencies through pacman, builds and runs the thread
policy test, then asks pacman to install the resulting package. Confirm the
replacement of `moonlight-qt` with `moonlight-qt-bc250` when prompted. Both
packages install `/usr/bin/moonlight`, so they cannot coexist.

The package uses system Qt, FFmpeg and rendering libraries. It includes ABI
dependencies for FFmpeg and libplacebo, uses the x86-64 baseline for compiler
architecture/tuning flags, and disables LTO and a separate debug package.
Other flags come from the local makepkg configuration. Pinning the source
does not make builds with different compilers or libraries byte-identical.
Windows/macOS prebuilts and the unused libsoundio submodule are not downloaded
for this Linux package.

Close any running test build, then launch `moonlight` from the menu or terminal.
The fork uses Moonlight's existing user settings and pairing data; installing
the package does not intentionally remove them. The executable still reports
the upstream application version 6.1.0. Check the fork package with:

```sh
pacman -Q moonlight-qt-bc250
pacman -Qo /usr/bin/moonlight
```

This is a distribution package, not a portable AppImage. A binary built on one
Arch/CachyOS installation may need rebuilding for different system libraries.
Fork updates are installed manually; the official `moonlight-qt` package does
not update this separately named package.

To return to the official package on an up-to-date Arch/CachyOS system:

```sh
sudo pacman -S moonlight-qt
```

Confirm removal of the conflicting BC-250 package when pacman asks.

Packaging references: [PKGBUILD](https://man.archlinux.org/man/PKGBUILD.5.en)
and [makepkg](https://man.archlinux.org/man/makepkg.8.en).
